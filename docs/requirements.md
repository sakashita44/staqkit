# 要求定義

## 前提

- 実験データ解析一般のベストプラクティスの視点で記述する。
- 手段（DB、ファイル、特定ツール等）は要求のレベルでは問わない。具体的なツール選択はアーキテクチャの判断とする。
- フレームワークが管理するデータは、意味的な識別子の組み合わせ（被験者、条件、計測種別、処理段階等）で一意に特定できることを前提とする。データ値の型（数値、テキスト、バイナリへのパス等）は問わないが、意味的座標を持たないデータは管理対象外である。
- データが管理下にあるか否かは、明示的な宣言行為（ステージ定義等）によって決まる。管理外のデータ（探索的な notebook 出力等）にフレームワークは関与しない。これは後述する設計ファーストの最初の現れである。

## 設計ファースト

フレームワークの全体を貫く姿勢は、実体に先立って契約を宣言することである。スキーマは実データに先立って宣言し、ノードは実装に先立って宣言し、出力インターフェースは実装に先立って定義する。データやコードが先にあってそこから構造を後付けするのではなく、構造の宣言が常に先行する。

この姿勢を支える動機が二つある。

ひとつは暗黙依存の外部化である。解析者の頭の中にある暗黙的な依存（データの意味、パラメータの経緯、処理の前提条件）を、契約として外部に取り出す。フレームワークの価値は、この外部化をどれだけ自然に促せるかで測られる。

もうひとつはデータ中心の因果である。常に求められているのはデータであり、解析はそのデータを生んだ手段である。問いの向きは「このデータはなぜこの形で存在するか」から「この解析がこのパラメータで適用されたから」へ向かう。意味・経緯・パラメータはデータの属性として、データから到達できる。

## 真に達成したいこと

暗黙依存を契約として外部化・明示し、既定では強制することで、未来の他者（未来の自分を含む）が内部を読まずに次の三つを成り立たせられる状態を保つこと。すなわち、過去の結果を再現でき（信頼）、データの意味と来歴に到達でき（理解）、各解析ステージを互いに影響されずに実装・拡張できる（独立）ことである。

設計の精神は次の三つの問いに集約される。

- 明日自分の席に別の人が座るとして、今までの結果をそのまま使えるか（信頼）。
- ある辺が上流ノードのどの部分を使っているかを、コードを読まずに把握できるか（理解）。
- ある解析ステージを、他ステージの内部を読まず、契約だけを頼りに独立して実装できるか（独立）。

## 信頼・理解・独立の三つの柱

要求は信頼・理解・独立の三つの柱に整理される。信頼の柱の大半は既存ツール（Git と DVC）に委譲され、フレームワーク固有の要求はごく一部に限られる。理解と独立の二つの柱が、フレームワークが固有に提供する価値の中心である。

核となる要求は次の七つである。

| 柱   | 要求                | 問い                       |
| ---- | ------------------- | -------------------------- |
| 信頼 | T1 来歴到達性       | いつ・何で作られたか       |
| 理解 | U1 意味的同一性     | どのデータのことか         |
| 理解 | U2 多軸クエリ面     | どう絞り込むか             |
| 理解 | U3 カタログ         | 何が存在するか             |
| 理解 | U4 意味到達性       | 何を意味するか             |
| 独立 | M1 契約強制         | 内部を読まずに実装できるか |
| 独立 | M2 不変性と純粋関数 | 他に影響しないか           |

### 信頼の柱

再現性・整合性・スナップショットといった信頼の中核は Git と DVC が提供する（後述「委譲する関心とツール」）。フレームワークが固有に担うのは来歴への到達性のみである。

**T1 来歴到達性**。あるデータを起点として、それがいつ、どのパラメータで、どの上流の実行から生成されたかに到達できる。再現性そのものは委譲し、フレームワークは実行事実を忠実に記録し、その記録へデータから到達できることを保証する。来歴の記録は信頼の産物であると同時に理解の入力でもあり、二つの柱を橋渡しする位置にある。

### 理解の柱

**U1 意味的同一性**。あるデータ片を、意味的座標（識別子の組み合わせ）によって曖昧さなく一意に指せる。「被験者1・条件A・左膝・角度・正規化済み」と言えば一つに定まる。物理パスや内部 ID ではなく、意味的座標がデータの正規の参照方法である。

**U2 多軸クエリ面**。任意の属性の組み合わせでデータを絞り込める単一の読み取り口を持つ。絞り込みの順序に依存しない。処理段階も属性の一つとして扱い、中間産物へのアクセスも同じインターフェースで行う。識別子自身が持つ構造化された属性（被験者 ID の身長・体重、データ種別の単位・意味等）も、スライスやフィルタの対象となる。

**U3 カタログ**。いま何のデータが存在し、それぞれがどんな定義（カラム・型・制約・説明）を持つかを、一覧・検索できる。定義は実データの有無に依らず引ける。

**U4 意味到達性**。データを起点として、それが何を意味し、どういう意図で作られたかに到達できる。到達の帰属単位は DAG のノードである。明示的な説明がコミット履歴の暗黙的な来歴を補完し、説明はデータと同一の管理単位に同居する。

### 独立の柱

**M1 契約強制**。各データの構造（スキーマと制約）は実データに先立って宣言され、既定では強制される。準拠しないデータは管理下に存在できない。これにより各ステージは、上流ステージの内部を読むことなく、宣言された契約だけを頼りに独立して実装・拡張できる。識別軸自身も構造化されたメタデータ（被験者 ID の身長・体重、データ種別の単位・意味等）を契約として持ちうる。契約の強制は開発中の高速な試行のために局所的に無効化できるが、無効化はあくまで非常口であり、強制が既定の状態である。

**M2 不変性と純粋関数**。処理ステップは、入力データとパラメータから新しいデータを生む純粋関数として表される。入力データを変更せず、過去の成果物の状態に影響を与えない。既存データへの加工は、常に新しいデータの生成として行う。これによりステージ間の副作用が排除され、各ステージを独立に扱える。

## 委譲する関心とツール

信頼の柱の中核は既存ツールに委譲し、フレームワークはその上の運用規約のみを定める。

| 委譲する関心                         | 委譲先            |
| ------------------------------------ | ----------------- |
| スナップショット再現性               | Git と DVC        |
| DAG 整合性・鮮度（有効/無効の判定）  | dvc status        |
| 部分再生成（影響部分木のみの再実行） | dvc repro         |
| スナップショット分岐                 | Git branch と DVC |

この委譲方針から、コマンド設計の原則が導かれる。信頼の柱に属する操作（スナップショットの固定、分岐、復元、マージ）は、原則としてフレームワークでラップせず、Git と DVC の標準操作に委ねる。理解と独立の柱に属する操作は、フレームワークが所有する。

## 基盤モデル

すべてのデータ間関係は有向非巡回グラフ（DAG）を形成する。ノードはデータであり、辺は処理ステップである。パラメータは辺に付随し、変更されると下流ノードが無効化される。各ノードは有効・無効・未生成の状態を持つ。

DAG はこのフレームワークの基盤モデルであるが、その追跡（整合性検証・鮮度判定・部分再生成）は DVC に委譲し、構築と循環検出には networkx を用いる。三つの柱は、この DAG の上に成り立つ。

探索もこのモデルの中で表現される。探索とは仮説的なノードと辺を作ることであり、確定とは実データを生成して有効な状態にすることである。正式と仮の二分法ではなく、ノードの状態遷移として扱う。

## 核要求から派生する事項

次の事項は核要求から導かれる制約・品質・設計パターンであり、独立した要求としては数えない。

**異質なデータ構造の共存**。時間軸・サンプリングレート・次元の異なるデータ（時系列、スカラー、メタデータ）が、それぞれの構造を保ったまま共存できる。これは多軸クエリ面が単一構造への正規化を強制しないという制約として現れる。

**管理境界のインターフェース**。管理外のデータを管理下へ昇格させる手段と、管理下のデータを管理外環境から利用する手段を提供する。管理下への参入は宣言的行為であり、設計ファーストの直接の帰結である。消費と流入の両方をカバーする。

**格納の中立性と拡張性**。格納形式が、実行可能な解析手法や格納可能なデータの種類を制約しない。新しい指標・処理段階・識別軸を追加しても、既存データへのアクセス方法が壊れない。既存識別子への属性追加も含む。これらは核要求を損なわないための品質制約である。

**リポジトリ境界を越えた合成**。別リポジトリの任意のノードを、新たな DAG の入力ノードとして取り込める。データ実体のコピーによる再現性と、出典元への参照保持による来歴追跡を両立する。これは核要求（単一の読み取り口、来歴到達性、意味到達性）をリポジトリ境界の外側にも成り立たせる、管理境界インターフェースの一般化である。

**解析プロセスの再利用と、解析と出力の分離**。解析処理を再利用可能な単位で切り出せること、解析ロジックと出力表現（グラフスタイル等）が分離され差し替えられること。これらはフレームワークの機構ではなく、望ましい設計パターンとして位置づける。出力パラメータは解析ではなく成果物に帰属する。

**設計時のステージ状態**。実装や実データに先立ってノードを宣言し、一時的に休止したステージを下流ごと管理から外す。これは必須の機能ではないが、設計ファーストの姿勢に合致し、最終成果物から逆算してノードを定義してから順に実装する作業を支える。

## 検証は自己契約の再帰

フレームワーク自身の設定ファイル（ステージ定義、テーブルスキーマ定義等）もまた、構造の保証を要するデータである。ユーザのデータに DDL による契約を課すのと同じ原理を、フレームワークは自分自身の設定にも適用する。設定ファイルの構文・外形・参照整合性の検証は、散発的な点検項目ではなく、設計ファーストをフレームワーク自身へ再帰的に適用したものとして一貫する。

## スコープの前提

- 利用者は基本的に1人である。同時アクセスはスコープ外とする。
- 他者への引き継ぎを考慮し、理解可能性とドキュメント性は必要とする。
- 責務境界は次のとおり。管理下データに対する契約の強制、来歴と意味への到達性、単一の読み取り口の提供が核の責務である。再現性は委譲する。管理境界をまたぐインターフェースの提供は責務に含む。

## フレームワークが依存しない利用文脈

探索的分析のワークフロー（notebook 等の管理外環境で探索し、結果を管理下へ昇格させる作業パターン）は、主要利用者の日常的な使い方として想定されるが、フレームワークの設計はこれに依存しない。フレームワークは管理境界のインターフェースを通じてこのワークフローを支えるが、探索そのものは管理しない。

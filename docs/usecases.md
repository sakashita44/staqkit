# ユースケース・シナリオ

## 位置づけ

staqkit の利用シナリオを体系化し、CLI 体系・Project 層の組み立て・外部連携などの設計判断を「想定される使われ方」から逆算するための入力とする。

各シナリオは以下の観点で記述する:

- **目的**: アクターが何を達成したいか
- **対応要求**: [requirements.md](requirements.md) のどの要求に対応するか
- **典型操作**: 利用者が実際に行う操作列
- **実現区分**: 実現手段の所属（後述の凡例）
- **補足**: 未仕様ポイント・設計判断の論点

## 凡例

### 実現区分

| 区分        | 意味                                                          |
| ----------- | ------------------------------------------------------------- |
| **CLI**     | `staqkit` コマンドが本体                                      |
| **Library** | Python API（`DataStore` 等）の直接利用。CLI ラップは任意      |
| **Git+DVC** | 既存ツールを直接運用。staqkit がラップするか否かは別判断      |
| **Pattern** | ステージ設計・運用慣習。コマンドや API ではなく構造として実現 |

| マーカー     | 意味                                          |

| **(検討中)** | 設計判断が未決。複数案がある状態              |

## A. ライフサイクル

プロジェクトの開始から公開・引き継ぎまでの長期的な状態遷移。

### A1. 新規プロジェクトを立ち上げる

- **目的**: 空のリポジトリから staqkit プロジェクトを開始する
- **対応要求**: 宣言の先行（構造の宣言が実体に先立つ起点）, 派生（格納中立性・拡張性）
- **典型操作**:
    1. リポジトリを作成
    1. プロジェクト雛形を生成（`copier copy` で `config/`, `stages/`, `data/` 等）
    1. 最初の table_schemas を定義（→ `staqkit validate --target schema` で随時確認）
    1. 最初のステージを追加（→ B1）
- **実現区分**: Pattern + CLI（プロジェクト初期化は Copier）
- **補足**: プロジェクト初期化は Copier 雛形が担い、`staqkit init` 相当の専用コマンドは設けない（→ [distribution.md](distribution.md)「初期化とステージ追加の責務分担」）。雛形を使わず手動配置でも成立する

### A2. 既存の解析作業に staqkit を後付け導入する

- **目的**: 既に手動運用している解析スクリプト・データに staqkit を段階的に被せる
- **対応要求**: 派生（管理境界インターフェース・拡張性）
- **典型操作**:
    1. 既存 data/ 配下を staqkit のディレクトリ規約に再配置
    1. 既存スクリプトを stage.yaml + run.py に翻訳（部分的でも可）
    1. table_schemas を既存データから逆算して定義
    1. `staqkit validate` で整合確認
- **実現区分**: CLI + Pattern
- **補足**: **(TODO)** 「部分導入」を許す段階的移行パターンの整理が必要。validate が「全部 staqkit 化されていない状態」を許容するかが論点

### A3. プロジェクトを引き継ぐ（受け渡し側）

- **目的**: 受け取り側が再現可能な状態でリポジトリを送り出す
- **対応要求**: 委譲（再現性）, U4
- **典型操作**:
    1. 全ステージの最新化（`staqkit repro`）
    1. `staqkit validate` で整合確認
    1. リモートへの push（Git + `dvc push`）
    1. README/docs の更新（→ D2 検査群: description 網羅）
- **実現区分**: CLI + Git+DVC

### A4. プロジェクトを引き継ぐ（受け取り側）

- **目的**: 受け取ったリポジトリで再現結果に到達する
- **対応要求**: 委譲（再現性）, U4
- **典型操作**:
    1. リポジトリを clone
    1. `uv sync` で依存復元
    1. `dvc pull` で実データ復元
    1. `staqkit validate` で整合確認
    1. 必要なら `staqkit repro` で再生成可能性を確認
- **実現区分**: Git+DVC + CLI
- **補足**: 受け渡し側のスナップショット品質次第で操作量が変わる。validate は `--target` で個別実行でき、「最小限の確認」のみで使い始める導線がある（→ [components/cli.md](components/cli.md#staqkit-validate)）

### A5. プロジェクトを公開する

- **目的**: 第三者が論文等の根拠データに到達でき、再現できる状態にする
- **対応要求**: U2, U4, 委譲（再現性）, 派生（リポジトリ境界を越えた合成）
- **典型操作**:
    1. 公開対象スナップショットの確定（→ F1）
    1. 意味到達性の最終チェック（→ D2 検査群: description 網羅）
    1. リモート（DVC remote, Git ホスティング）への push
- **実現区分**: CLI + Git+DVC + Pattern
- **補足**: 「アーカイブ＝以後編集不可状態」は持たない。公開後のリポジトリも編集可能であり、ある時点のスナップショットが tag として参照可能な状態が「公開」の定義。第三者向け IF は標準構造（stages/, config/, data/stages/）そのものが提供（→ external-data.md「上流の公開IF」）

### A6. 親プロジェクトのデータを参照する形で新プロジェクトを立ち上げる

- **目的**: 1つ以上の既存 staqkit プロジェクトのデータを参照して、新しい解析プロジェクトを開始する
- **対応要求**: 派生（リポジトリ境界を越えた合成）
- **典型操作**:
    1. 新リポジトリを作成（→ A1）
    1. 親プロジェクトのデータを `dvc import` で取り込む（→ C2）
    1. 新規解析を追加（→ B1）
- **実現区分**: CLI + Pattern
- **補足**: 親が複数（2つ以上の親プロジェクトを持つ立ち上げ）も本シナリオに含む。`dvc import` の標準パターンで親毎に取り込むだけで成立する。テンプレートコピー（親の構造を初期値としてコピーする形）は派生ではなく A4（引き継ぎ受け取り側）と等価のため本シナリオには含めない。取り込んだ親データは生データ同様のソース扱いとし、取り込みステージ（`--template ingest`）で自プロジェクトのスキーマに従って DataStore に統合する（→ C2 補足、[external-data.md](components/external-data.md)）。スキーマ転送は不要。

### A7. 実行環境・依存の更新に追従する

- **目的**: 依存ライブラリ更新（uv lock 更新、Python バージョン更新等）を取り込む
- **対応要求**: 委譲（再現性）
- **典型操作**:
    1. `uv lock --upgrade` で依存更新
    1. `staqkit repro` で全ステージを再実行し結果が一致することを確認
    1. 不一致発生時は原因調査・該当ステージのパラメータ調整
    1. 更新後の `uv.lock` を Git commit
- **実現区分**: CLI + Pattern
- **補足**: 依存環境含めての再現性（委譲する関心）が前提であり、`uv.lock` は Git 管理対象。スナップショット tag は `uv.lock` も含む形で固定される。本シナリオは依存更新に伴う運用ガイドライン的位置付け

### A8. リモートを別に移す

- **目的**: DVC リモート（S3, GDrive 等）または Git ホスティングを別の場所に移行する
- **対応要求**: 委譲（再現性）
- **典型操作**:
    1. 新リモートを設定（`dvc remote add` / `git remote add`）
    1. 新リモートに push（`dvc push` / `git push`）
    1. 旧リモートの参照を切替（`dvc remote default` / `git remote set-url`）
- **実現区分**: Git+DVC
- **補足**: staqkit ラップは不要。DVC/Git の標準操作で完結

### 考慮外シナリオ

以下は staqkit のスコープ外として明示する。

- **既存プロジェクトの分割**: 1つの staqkit プロジェクトを複数に分割するシナリオは扱わない。分割が必要な場合は新規プロジェクトを作成し、A6 として既存プロジェクトを親に取り込む形を想定
- **内部構造を維持したままのプロジェクト統合**: 2つの staqkit プロジェクトの内部構造（DAG・stage.yaml 群）を一つにマージするシナリオは扱わない。「2つ以上のプロジェクトを親に持つ新プロジェクト」の形態は A6 で扱う
- **DAG 合成**: 複数の staqkit プロジェクトの DAG 構造を直接共有する形態（submodule 等による DAG 共有）は扱わない。データ参照は A6 / C2 の外部データ取り込みで実現する
- **ブランチ分岐の自動マージ**: 同一プロジェクト内で並走した解析（→ F2 分岐）の自動マージはツール側では保証しない。マージ判断はユーザの責務

## B. 開発・解析作業

日常的な解析作業のシナリオ。

### B1. 新ステージを追加する

- **目的**: 新しい処理ステップを DAG に追加する
- **対応要求**: 派生（拡張性）
- **典型操作**:
    1. `staqkit add-stage <path>` で雛形生成（→ [cli.md](components/cli.md#staqkit-add-stage)）
    1. stage.yaml に inputs/outs と params 束縛（外部 params ファイルへの参照）を記述
    1. run.py に処理を実装
    1. `staqkit validate` で参照整合性確認
    1. `staqkit repro <stage>` で実行
- **実現区分**: CLI
- **補足**: add-stage コマンドの仕様は [cli.md](components/cli.md#staqkit-add-stage)。実装なしで仕様だけ先に固定する仮追加（planned 状態）は G3 を参照

### B2. パラメータを変えて再実行する

- **目的**: 既存ステージのパラメータを調整して結果を比較する
- **対応要求**: 委譲（部分再生成）, T1
- **典型操作**:
    1. params ファイルの値を編集（束縛先を変える場合のみ stage.yaml の `params` を編集）
    1. `staqkit repro <stage>` で部分再生成
    1. `staqkit history <stage>` で過去実行と比較
- **実現区分**: CLI
- **補足**: 手動でのパラメータ探索（複数の値を順に試して結果を見る）は本シナリオの繰り返し + E2 履歴一覧（dvc.lock の params 変遷）で対応可能。専用の探索支援機構は持たない。最適化のような自動探索が必要な場合は最適値を出力するステージとして通常通り設計する

### B3. 上流データの更新を下流に伝播させる

- **目的**: 生データや上流ステージの変更を下流ステージに反映する
- **対応要求**: 委譲（DAG整合性・鮮度・部分再生成）
- **典型操作**:
    1. 上流データ変更（生データ差し替え、上流ステージ再実行等）
    1. `staqkit status` で影響範囲を確認
    1. `staqkit repro` で全下流を再生成、または `staqkit repro <stage>` で限定的に
- **実現区分**: CLI
- **補足**: データの後追い追加（少人数被験者で解析実装を済ませてから全被験者データに拡張する等）も「上流データ変更 → 下流再実行」の同型シナリオとして本ケースで扱う

### B4. 特定ステージの上流依存を確認する

- **目的**: 「このステージは何に依存しているか」を把握する
- **対応要求**: T1, U4
- **典型操作**:
    1. `staqkit dag` で全体構造を可視化
    1. 個別ステージの依存は stage.yaml の inputs/extra_deps を参照
- **実現区分**: CLI

### B5. テーブル定義（カラム一覧）を調べる

- **目的**: 「このテーブルにはどんなカラムがあるか」を把握する
- **対応要求**: U3, U4
- **典型操作**: `staqkit schema`（定義テーブル一覧）または `staqkit schema <table>`（単一テーブルのカラム・制約）を実行
- **実現区分**: CLI
- **補足**: B5・B6・B7 は「どんなデータが在り何を意味するか調べる」という一つの調査意図のアクセス経路違い（定義一覧 / 特定カラム / 実データ）であり、それぞれ構造の内省 `staqkit schema`・カラム横断 `staqkit column`・実データの目録 `staqkit catalog` が対応する（→ [cli.md](components/cli.md#スキーマ内省カタログ出力)）

### B6. 特定カラムの定義・FK 関係を調べる

- **目的**: 「`uid` ってなんだ？」「どのテーブルにある？」を把握する
- **対応要求**: U3, U4
- **典型操作**: `staqkit column <name>` で全テーブルでの出現箇所と FK 関係を表示
- **実現区分**: CLI

### B7. テーブルの内容（実データ）を一覧する

- **目的**: 「このテーブルに今どんなレコードが入っているか」を把握する
- **対応要求**: U3
- **典型操作**: テーブル内容を出力するコマンドを実行（`staqkit catalog` の責務）
- **実現区分**: CLI
- **補足**: 実データの目録出力は `staqkit catalog` が担う（→ [cli.md](components/cli.md#staqkit-catalog)）

### B8. 失敗ステージの原因を調査する

- **目的**: 実行エラーや想定外の出力の原因を特定する
- **対応要求**: T1
- **典型操作**:
    1. `staqkit history <stage>` で過去実行を確認
    1. `staqkit provenance <stage>` で来歴チェーンを辿る
    1. 当時の commit の dvc.lock で実行時パラメータを参照
- **実現区分**: CLI

### B9. ステージを一時休止/再開する

- **目的**: 実験的なステージや一時的に不要なステージを管理から外す/戻す
- **対応要求**: 派生（設計時のステージ状態）
- **典型操作**:
    1. stage.yaml の status を `inactive` に変更
    1. `staqkit clean` で休止データの整理
    1. 再開時は status を `active` に戻して `staqkit repro`
- **実現区分**: CLI + Pattern

### B10. 多軸スライスでデータを取り出す

- **目的**: 「被験者1・条件A・正規化済み」など意味的座標で実データを引く
- **対応要求**: U1, U2
- **典型操作**: notebook/run.py 内で `DataStore.query(table, filters)` を呼ぶ
- **実現区分**: Library
- **補足**: 日常アクセスの中核。CLI ラッパー（探索目的の薄いラッパー）を提供するかは **(検討中)**

### B11. 識別軸メタデータでフィルタする

- **目的**: 「身長 > 170 の被験者だけ」「単位が rad の計測種別だけ」など、識別子の属性に基づくスライス
- **対応要求**: U2（識別子の属性もスライスやフィルタの対象となる、と明記）
- **典型操作**: `DataStore.query()` でテーブル単位に取得し、polars 側で結合・絞り込む。または `DataStore.fetch()` で FK を辿る JOIN と範囲条件を SQL で書く
- **実現区分**: Library
- **補足**: 識別子の属性は当該テーブルのカラムであり、属性による絞り込みは query + polars か fetch で行う。`query()` は等値/IN・単一テーブルに閉じ、属性テーブルへの JOIN を内蔵しない（→ [datastore.md](components/datastore.md#識別子と属性の表現)）

### B12. 新しい被験者・条件を追加する（識別軸の語彙拡張）

- **目的**: 既存の識別軸に新しい値（新被験者ID、新条件名等）を追加する
- **対応要求**: 派生（拡張性）（新しい識別軸の追加、と明記）
- **典型操作**:
    1. 新値を含むデータを生成するステージを実行（値は行として追加され、スキーマ変更を伴わない）
    1. `staqkit validate` で整合確認
- **実現区分**: CLI + Pattern
- **補足**: 識別子の語彙は当該テーブルに実在する PK 値の集合であり、値の追加は行の追加。スキーマは変わらず、生成ステージの再実行で反映する。B12・B13・B16 は「識別軸の進化」クラスタ（値の追加 / 属性の追加・変更 / 値の削除）を成すが、行追加（B12・B16）と DDL 変更（B13）で影響範囲が異なる（→ [datastore.md](components/datastore.md#語彙の進化と削除)）

### B13. 識別子の属性を追加・変更する

- **目的**: 被験者IDに体重を後付けする、データ種別の単位定義を変更する等
- **対応要求**: 派生（拡張性）（既存識別子への属性追加、と明記）
- **典型操作**:
    1. table_schemas の該当テーブル定義に column を追加 / 変更
    1. 生成ステージを再実行して既存データを再生成
    1. `staqkit validate` で整合確認
- **実現区分**: CLI + Pattern
- **補足**: カラムの追加・変更は DDL 変更であり、同名テーブルを出力する全ステージの schema 契約を一斉に変える破壊的変更。既存 parquet はスキーマ準拠検査（`on_read: schema` / `staqkit validate`）で非準拠として検出され、生成ステージの再実行で解消する。マイグレーションは in-place 変換でなく再生成を指し、新カラムのデフォルト値も run.py の再生成側で与える（staqkit はバックフィル機構を持たない）（→ [datastore.md](components/datastore.md#語彙の進化と削除)）

### B14. ステージをリファクタする

- **目的**: 結果（出力データ）を変えずにステージの実装を変更する
- **対応要求**: -（B14 固有の staqkit 責務はなし）
- **典型操作**:
    1. リファクタ前の commit に tag を打つ等で参照可能にする
    1. run.py を編集
    1. `staqkit repro <stage>` で再実行し、リファクタ前と数値が一致することを確認（数値の差分比較はユーザの責務）
- **実現区分**: Library + Pattern
- **補足**: 結果の数値一致を保証する機構は B14 固有では持たない（差分比較はユーザ責務）。一方、出力の「形」については以下が標準提供されており、リファクタ後の repro でも自動的に検査される:

    - 出力スキーマ（カラム構成 vs DDL）の検証 — `DataStore.write_table` 書き込み時（Library）
    - 宣言 outs と実出力ファイルの整合検証 — run_stage エピローグ（Project 層）

    したがって「リファクタによりスキーマ契約が壊れた」ケースは repro 時点で検出される。数値比較は B17（結果比較）+ F1/F3 のスナップショット参照 + B3 再実行の組み合わせで運用

### B15. ステージを削除する

- **目的**: 不要になったステージを DAG から完全に取り除く
- **対応要求**: 派生（設計時のステージ状態）
- **典型操作**:
    1. 当該ステージを参照する下流ステージの stage.yaml を編集（参照切断 or 代替ソース指定）
    1. 当該ステージのディレクトリ（stages/xxx/, data/stages/xxx/）を削除
    1. `staqkit clean` で残った孤児データを整理（→ D5）
    1. `staqkit validate` で参照整合性を確認
- **実現区分**: CLI + Pattern
- **補足**: 下流が `source_stage` で当該ステージを参照したまま削除すると、参照整合性検査（→ D2）が参照先不在を検出してエラーになる（警告のみで通す緩和経路は設けない）。したがって「下流の参照を切断（編集 or 代替ソース指定）→ ディレクトリ削除 → clean で孤児整理」の順で行う。B9 一時休止（可逆・データ保持）と異なり永久削除であり、可逆な休止が要るなら inactive を用いる（→ [stage.md](components/stage.md#ステージの削除)）

### B16. 識別子の値を削除する

- **目的**: 既存の識別軸から特定の値（被験者 ID、条件名等）を取り除く
- **対応要求**: 派生（拡張性）（B12 の逆操作）
- **典型操作**:
    1. 当該値の行を除いてデータを再生成（生成ステージの再実行）
    1. `staqkit validate` で整合確認
- **実現区分**: CLI + Pattern
- **補足**: 値の削除は行の削除であり、B12 の逆操作。当該値を参照していた行も再生成して参照を除けば、FK 参照の不整合は残らない。staqkit はカスケード削除も孤立行の専用検査も持たないため、参照先を失った行は検出されない（→ [datastore.md](components/datastore.md#語彙の進化と削除)）

### B17. 解析結果を比較する

- **目的**: パラメータ変更や分岐の前後で、解析結果（出力データ・数値）がどう変わったかを比較する
- **対応要求**: T1, 委譲（スナップショット分岐）
- **典型操作**:
    1. `staqkit history <stage>`（dvc.lock の params 変遷）で各実行のパラメータを突き合わせる
    1. `git diff` で stage.yaml / run.py の差分を確認
    1. 各スナップショット（→ F1/F3）の出力データを取り出して数値を比較
- **実現区分**: CLI + Git+DVC + Pattern
- **補足**: ツールチェーンが提供するのは比較に必要な材料（dvc.lock の params・出力ハッシュ、スナップショット参照）まで。数値 diff 自体の標準化（比較レポート生成等）は持たず、ユーザが担う。B2 パラメータ探索・B14 リファクタの数値一致確認はいずれも本 UC の組み合わせで運用。**(検討中)** 比較支援を staqkit が薄く提供する価値があるか

### B18. 未知のプロジェクトを読み解く

- **目的**: 自分が構築していない staqkit リポジトリの構造・データ・意味を把握する
- **対応要求**: U2, U3, U4, T1
- **典型操作**:
    1. `staqkit dag` で全体構造を俯瞰（→ D6）
    1. 定義・カタログを調べる（→ B5/B6/B7）
    1. 気になるデータの来歴を辿る（→ E1）
    1. 各ステージの README.md / desc / column_descriptions で意図を読む
- **実現区分**: CLI + Library + Pattern
- **補足**: 理解の観点の総合的な入口であり、個別経路（B4〜B7, D6, E1）を束ねる。A4（引き継ぎ受け取り側）が「再現に到達する」体験であるのに対し、本 UC は「意味と構造を理解する」体験。第三者がツールチェーンを通して staqkit プロジェクトを読み解く際の中核

## C. 外部成果物・連携

成果物の外部利用と外部リポジトリとの連携。論文・レポート等の特定用途は本カテゴリの一般シナリオで扱い、専用シナリオは設けない。

### C1. 成果物を外部にエクスポートする

- **目的**: ステージ出力データを外部用途（論文、レポート、別解析プロジェクト等）で利用可能にし、来歴も含めて第三者に追跡可能な形で提供する
- **対応要求**: U2, 委譲（再現性）, T1
- **典型操作**:
    1. 出力したいデータを生成するステージを `staqkit repro` で確定
    1. 出力対象は `data/stages/<stage>/` の parquet として既に確定済み
    1. 配布手段はユースケースに応じて選択:
        - 同プロジェクトの clone を共有（最も再現性が高い）
        - 別 repo から `dvc import` で参照（→ C2）
        - parquet を手動コピー（来歴は別途明示）
    1. 来歴は `staqkit provenance <stage>` で取得し、commit hash を成果物に併記
- **実現区分**: CLI + Pattern + Git+DVC
- **補足**: 専用 export コマンドは持たない。出力データは必ずステージ出力として運用することで来歴を保証する設計が前提（中間生成物を export 対象にする場合は、別ステージとして DAG に組み込む）。論文・レポート等の特定用途も本シナリオで扱い、用途別の特別な処理は設けない

### C2. 別リポジトリのデータを取り込む

- **目的**: 他プロジェクトの解析結果を入力ノードとして利用する
- **対応要求**: 派生（リポジトリ境界を越えた合成）
- **典型操作**: `dvc import <url> <path>` で取り込み（→ external-data.md）
- **実現区分**: Git+DVC
- **補足**: 取り込んだデータは DataStore へ直接は載せず、生データ同様のソースとして扱う。下流の取り込みステージ（`staqkit add-stage --template ingest`）が `extra_deps` でファイルとして読み、加工結果を自プロジェクトの `config/table_schemas/` に従って DataStore に登録する（→ [external-data.md](components/external-data.md)「ソースとしての扱い」）。`dvc import` で table_schemas を伝達する必要はなく、追跡性は import の `repo.url` + `rev_lock` が担保する。A6 親プロジェクト参照立ち上げも同じ扱い

#### C2a. 取り込みノードの来歴を出典元 DAG まで追跡する

- **目的**: 取り込んだデータが出典元でどう生成されたかを辿れる
- **対応要求**: T1（出典元 DAG への参照を通じて来歴が追跡可能、と明記）
- **典型操作**:
    1. 取り込みデータの `.dvc` ファイルから `repo.url` と `rev_lock`（commit hash）を取得
    1. 出典元リポジトリを別途 clone（`git clone --branch <hash>` 等）
    1. clone 先で通常の `staqkit provenance` を実行
- **実現区分**: Git+DVC + Pattern
- **補足**: `dvc import` が記録する `rev_lock` + `repo.url` がスナップショット参照として機能する。staqkit 側の追加ラップは不要。staqkit の責務は「参照を辿れる構造を保証する」ことに留まり、辿る操作自体はユーザが Git で行う（→ external-data.md「追跡性」）。`dvc import` が出典元の来歴を自リポへ同梱する仕様は持たない。出典元を clone すれば、その `dvc.lock` + git 履歴から通常どおり来歴を導出でき、DVC remote へのアクセスは不要（→ stage.md「来歴の所在」）

#### C2b. 取り込み元 DAG の更新を反映する

- **目的**: 出典元リポジトリの最新版を自プロジェクトに取り込み直す
- **対応要求**: 派生（リポジトリ境界を越えた合成）
- **典型操作**: `dvc update <path>` で取り込み先を更新
- **実現区分**: Git+DVC
- **補足**: external-data.md「取り込み」で `dvc update` による明示的追従が方針として確定。更新検知の自動化は現状未対応（手動判断）

#### C2c. 自プロジェクトの一部を外部公開 IF として整備する

- **目的**: 他プロジェクトから取り込まれることを前提に、自プロジェクトの出力を整備する
- **対応要求**: 派生（リポジトリ境界を越えた合成）（U2, U3, U4 が外部に対しても成立することの確認）
- **典型操作**: 通常の運用（standard structure 維持 + description 充実 + スナップショット確定）でそのまま外部公開 IF として機能
- **実現区分**: Pattern
- **補足**: 標準構造（stages/, config/, data/stages/）自体が外部 IF として機能するため、追加整備は原則不要（external-data.md「上流の公開IF」）。整備対象は通常の品質改善（→ D2 検査群: description 網羅、A5 公開シナリオ）と同じ

### C3. プロジェクト構造ドキュメントを書き出す

- **目的**: README や docs 用に DAG 構造・テーブル定義一覧をドキュメント化する
- **対応要求**: U3, U4
- **典型操作**:
    1. 必要な情報を出力する B 系コマンドを実行（B5 テーブル定義一覧、B6 column、B7 テーブル内容、D6 dag 等）
    1. stdout をパイプで Markdown ファイル等に保存
    1. リポジトリ内 docs に配置
- **実現区分**: CLI + Pattern
- **補足**: staqkit が提供するのは stdout 出力までであり、ファイル書き出しやフォーマット変換のパイプ処理は責務外。ドキュメント書き出し専用の固有コマンドは設けず、B 系コマンド（schema / column / catalog / dag）の stdout をパイプで保存する形で対応する

## D. 健全性・検証

利用者が Git+DVC+staqkit のツールチェーン全体で「いま健全か」を確かめる体験。検査の実装単位ではなく、利用者の検証意図でシナリオを立てる。個別の検査項目は D2（全体健全性の保証）が内包する「検査群」として整理し、それ自体は検証コンポーネントへの要求として扱う。

### D1. 編集中に局所整合をすぐ確かめる

- **目的**: いま編集している stage.yaml / table_schemas の構文・参照だけを素早く検査し、編集ループを止めない
- **対応要求**: 検証（自己契約の再帰）
- **典型操作**: 編集対象に絞った検査を実行（pre-commit フック、または対象を限定した検査呼び出し）
- **実現区分**: CLI + Pattern
- **補足**: D2 のフル検査は時間がかかり編集サイクルに組み込みにくい。「いま触っている部分だけ」を検査する個別実行は `staqkit validate --target schema|references|descriptions` で行う（→ [components/cli.md](components/cli.md#staqkit-validate)）。D2 の検査群のうち構文・外形（stage.yaml / table_schemas）と参照整合性が本 UC の主対象

### D2. 引き継ぎ・公開前に全体健全性を保証する

- **目的**: リポジトリ全体が自己契約に準拠し、再現・理解可能な状態にあることを一括で保証する
- **対応要求**: 検証（自己契約の再帰）, M1 契約強制, U4, T1
- **典型操作**: 全体検査（`staqkit validate`）を実行し、鮮度（→ D3）・再現性（→ D4）と併せて公開/引き継ぎの可否を判断する
- **実現区分**: CLI + Git+DVC
- **補足**: A3（引き継ぎ受け渡し）・A5（公開）が呼ぶゲート。保証が要求する検査群は次のとおりで、各検査がどの観点を満たすかを併記する。これらは検証コンポーネントへの要求であり、個別実行は `staqkit validate --target` で提供する（→ [components/cli.md](components/cli.md#staqkit-validate)）

| 検査群           | 内容                                                                                                                                     | 満たす観点 | 実装                    |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ---------- | ----------------------- |
| 構文・外形       | stage.yaml / table_schemas の必須フィールド・型・構造、埋め込み DDL 構文                                                                 | 検証       | Pydantic + sqlglot      |
| 参照整合性       | stage.yaml 間 `source_stage` の実在・循環なし（DAG 構造）                                                                                | 検証       | networkx                |
| params 束縛解決  | `params` の各束縛が指す `file` の実在と `key`（ネストパス）の存在。ローカル名の重複は YAML キー一意性で検出                              | 検証       | —                       |
| スキーマ準拠     | `data/stages/*` の parquet が DDL に準拠                                                                                                 | M1         | DDL パース + 検証クエリ |
| FK 整合性        | TableSchemaSet の FK 参照先テーブルの存在・型一致                                                                                        | M1         | —                       |
| description 網羅 | ノード・カラムの説明（desc 欄 / README.md / column_descriptions）の欠落検出                                                              | U4         | —                       |
| パラメータ整合   | params 編集の鮮度は dvc status（D3）が検出。来歴（params・ハッシュ）は dvc.lock + git 履歴を源泉とし独立記録を持たないため整合検査は不要 | T1         | dvc status / Git        |
| 外部参照解決     | 取り込みポインタ（repo.url + rev_lock）の構造的整合（記録の存在・形式）。runtime 到達性は DVC 責務で対象外                               | T1         | ReferenceIntegrityError |

スキーマ準拠検査はステージ実行時の `DataStore.write_table` 書き込み（Library）でも局所的に行われ（→ B14）、本 UC はリポジトリ全体を横断検査する役割。検査群は `staqkit validate --target` で個別実行できる。description 網羅検査は Layer1（stage.yaml desc 非空）・Layer2（README.md 存在）・column_descriptions（全カラム説明）の充足を warning で報告する（Layer3 の外部参照は任意のため対象外）。キャッチオール検査対象ファイルの具体的列挙は実装時に確定する。クロスリポのスキーマ整合性検査は外部データをソース扱いとする方針（[external-data.md](components/external-data.md)）により不要となり、取り込みポインタの構造整合は外部参照解決検査（`ReferenceIntegrityError`）でカバーする

### D3. 再実行が要るステージを知る（鮮度）

- **目的**: どのステージが再実行を要するかを把握する（上流データ変更による下流の鮮度低下検出）
- **対応要求**: 委譲（DAG整合性・鮮度）
- **典型操作**: `staqkit status` を実行
- **実現区分**: CLI
- **補足**: dvc.yaml は staqkit 全体として派生物扱いであり Git 非管理（→ [architecture.md](architecture.md) / [components/pipeline-gen.md](components/pipeline-gen.md)）。`staqkit status` は repro 等と同じ生成プロローグを共有した上で `dvc status` を呼ぶラッパーであり、動的生成は本 UC 固有の付加価値ではない。`dvc status` の出力分類のうち changed deps が本 UC の主関心、missing data + changed outs は再現性確認（→ D4）の関心。**(検討中)** planned/inactive の表示や stage 状態併記など、出力フォーマット拡張の要否

### D4. clone した状態が再現できているか確認する

- **目的**: clone した状態が固定スナップショットと一致しており、再現可能な状態にあることを確認する
- **対応要求**: 委譲（再現性）
- **典型操作**:
    1. リポジトリを clone
    1. `uv sync` で依存復元
    1. `dvc pull` で実データ復元
    1. `staqkit status` で差分なし（全ステージが up-to-date）を確認
- **実現区分**: CLI + Git+DVC
- **補足**: A4 受け取り側の最終チェックとしても利用される。**(検討中)** 「再現できているか」を明示判定する専用フラグ（`staqkit status --check` 等）を提供するか、`staqkit status` の出力解釈で十分か

### D5. 不要・孤児・inactive データを片付ける

- **目的**: 不要なデータディレクトリを検出・削除する
- **対応要求**: 派生（設計時のステージ状態）
- **典型操作**: `staqkit clean` で検出 → `--remove` で削除
- **実現区分**: CLI

### D6. 全体像（planned 含む）を俯瞰する

- **目的**: 未生成ステージも含めた全体構造を視覚化する
- **対応要求**: U3, 派生（設計時のステージ状態）
- **典型操作**: `staqkit dag` を実行
- **実現区分**: CLI

## F. スナップショット・分岐

DAG の時間的進化と並行探索。いずれも信頼の観点に属する操作であり、固定・分岐・復元・マージは原則として staqkit でラップせず Git+DVC の標準操作に委ねる（→ [requirements.md](requirements.md)「委譲する関心とツール」）。薄い利便ラッパーを将来追加する余地は残すが、必須ではない。

### F1. スナップショットを切る/タグ付ける

- **目的**: 論文投稿時点、レビュー対応前後など節目で DAG 状態を固定する
- **対応要求**: 委譲（再現性・分岐）
- **典型操作**: `git tag <name>` + `dvc push` で実データも含めてリモートに固定
- **実現区分**: Git+DVC
- **補足**: 原則として素の Git+DVC で運用する（委譲方針）。`staqkit snapshot tag` 等の薄い利便ラッパーを将来追加する余地は残すが必須ではない

### F2. 解析パスを分岐させる

- **目的**: 同じ上流データから複数の解析方針を並行探索する
- **対応要求**: 委譲（スナップショット分岐）
- **典型操作**: `git checkout -b <branch>` で分岐 → 各ブランチで stage.yaml を編集
- **実現区分**: Git+DVC
- **補足**: F1 と同じく原則非ラップ。薄い利便ラッパーの余地のみ残す

### F3. 過去スナップショットへ復元する

- **目的**: 不整合や事故からの原状復帰、または過去状態の再現
- **対応要求**: 委譲（再現性）
- **典型操作**: `git checkout <tag>` + `dvc checkout`
- **実現区分**: Git+DVC
- **補足**: F1 と同じく原則非ラップ。薄い利便ラッパーの余地のみ残す

### F4. 別系統の結果をマージする

- **目的**: 分岐した DAG の合流（並行探索の結果統合）
- **対応要求**: 委譲（スナップショット分岐）
- **典型操作**: `git merge` + DVC コンフリクト解決
- **実現区分**: Git+DVC
- **補足**: マージ操作自体は原則非ラップ（Git+DVC 標準）。ただし DVC 管理ファイルのコンフリクト解決パターンは未整理で **(TODO)**

## G. 管理境界

管理下と管理外（notebook 等）の境界をまたぐ操作。

### G1. notebook 探索結果を管理下に昇格させる

- **目的**: notebook で得た探索結果を staqkit ステージとして固定する
- **対応要求**: 派生（管理境界インターフェース）, 文脈（探索的ワークフロー）
- **典型操作**:
    1. notebook で得たコード・データを stage.yaml + run.py に翻訳
    1. 出力 IF（outs）を宣言
    1. `staqkit repro <stage>` で管理下に確定
- **実現区分**: Library + CLI + Pattern
- **補足**: 翻訳作業自体はユーザの責務。staqkit が提供するのは昇格先の構造（stage.yaml/run.py 規約）と、昇格後に notebook 側から管理下データを参照可能にする Library（→ G2）。専用支援コマンドは持たない

### G2. 管理下データを管理外環境から消費する

- **目的**: notebook やアドホックスクリプトから staqkit 管理下のデータを読む
- **対応要求**: 派生（管理境界インターフェース）
- **典型操作**: notebook 内で `open_scoped_store(root, up_to=...)` で読み取り専用 DataStore を得て `query()` で取得（→ [datastore.md](components/datastore.md#入口)）
- **実現区分**: Library

### G3. 出力 IF を先に定義して planned ノードを作る

- **目的**: 実データ未生成のまま下流の処理ステップを設計する
- **対応要求**: 派生（設計時のステージ状態）, 基盤モデル（ノード状態）
- **典型操作**:
    1. stage.yaml に `status: planned` で outs 宣言
    1. 下流ステージは planned ノードを参照可能
    1. 後で run.py を実装 → `status: active` → `staqkit repro`
- **実現区分**: CLI + Pattern
- **補足**: `staqkit add-stage --status planned` で支援可能（→ [cli.md](components/cli.md#staqkit-add-stage)）

## H. 再利用

DAG の辺（処理）の再利用。requirements.md では核要求から派生する設計パターン（解析プロセスの再利用、解析と出力の分離）として位置づけられる。

### H1. 共通解析プロセスを別プロジェクトで再利用する

- **目的**: 切り出した処理ステップ（フィルタリング、正規化等）を別プロジェクトに移植する
- **対応要求**: 派生（解析プロセスの再利用）
- **典型操作**:
    1. 再利用対象ステージのディレクトリを別プロジェクトにコピー
    1. table_schemas の該当部分も移植
    1. 別プロジェクト側で参照を繋ぎ直す
- **実現区分**: Pattern
- **補足**: **(TODO)** ステージの移植性を担保する仕組みの方向性が未整理

### H2. 同じ解析結果から異なるスタイルの図表を生成する

- **目的**: 解析ロジックを変えずに、出力表現（グラフスタイル等）だけ差し替える
- **対応要求**: 派生（解析と出力の分離）（出力パラメータは解析ではなく成果物に帰属する）
- **典型操作**:
    1. 解析ステージと出力ステージを分離した設計にする
    1. 出力ステージのパラメータのみ変更して `staqkit repro <出力ステージ>`
- **実現区分**: Pattern

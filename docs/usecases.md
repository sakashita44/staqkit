# ユースケース・シナリオ

## 位置づけ

本ドキュメントは staqkit の利用シナリオを体系化したもの。CLI 体系、Framework 層の組み立て、外部連携などの設計判断を「想定される使われ方」から逆算するための入力として機能する。

各シナリオは以下の観点で記述する:

- **目的**: アクターが何を達成したいか
- **対応要求**: [requirements.md](requirements.md) のどの要求に対応するか
- **典型操作**: 利用者が実際に行う操作列
- **実現区分**: 実現手段の所属（後述の凡例）
- **補足**: 未仕様ポイント・設計判断の論点

## 凡例

### 実現区分

| 区分        | 意味                                                          |
| ----------- | ------------------------------------------------------------- |
| **CLI**     | `staqkit` コマンドが本体。コマンド体系設計の対象（→ #10）     |
| **Library** | Python API（`DataStore` 等）の直接利用。CLI ラップは任意      |
| **Git+DVC** | 既存ツールを直接運用。staqkit がラップするか否かは別判断      |
| **Pattern** | ステージ設計・運用慣習。コマンドや API ではなく構造として実現 |

## A. ライフサイクル

プロジェクトの開始から公開・引き継ぎまでの長期的な状態遷移。

### A1. 新規プロジェクトを立ち上げる

- **目的**: 空のリポジトリから staqkit プロジェクトを開始する
- **対応要求**: 派生（格納中立性・拡張性）
- **典型操作**:
    1. リポジトリを作成
    2. プロジェクト雛形を生成（`config/`, `stages/`, `data/` 等）
    3. 最初の table_schemas を定義（→ 横断的観点: 編集時バリデーション支援、[idea.md](idea.md)）
    4. 最初のステージを追加（→ B1）
- **実現区分**: CLI（雛形生成は **(TODO)** `staqkit init` 相当が未仕様）
- **補足**: 雛形生成の必要性自体が論点。`uv init` + 手動配置でも成立する

### A2. 既存の解析作業に staqkit を後付け導入する

- **目的**: 既に手動運用している解析スクリプト・データに staqkit を段階的に被せる
- **対応要求**: 派生（管理境界インターフェース・拡張性）
- **典型操作**:
    1. 既存 data/ 配下を staqkit のディレクトリ規約に再配置
    2. 既存スクリプトを stage.yaml + run.py に翻訳（部分的でも可）
    3. table_schemas を既存データから逆算して定義
    4. `staqkit validate` で整合確認
- **実現区分**: CLI + Pattern
- **補足**: **(TODO)** 「部分導入」を許す段階的移行パターンの整理が必要。validate が「全部 staqkit 化されていない状態」を許容するかが論点

### A3. プロジェクトを引き継ぐ（受け渡し側）

- **目的**: 受け取り側が再現可能な状態でリポジトリを送り出す
- **対応要求**: 委譲（再現性）, U4
- **典型操作**:
    1. 全ステージの最新化（`staqkit repro`）
    2. `staqkit validate` で整合確認
    3. リモートへの push（Git + `dvc push`）
    4. README/docs の更新（→ D7）
- **実現区分**: CLI + Git+DVC

### A4. プロジェクトを引き継ぐ（受け取り側）

- **目的**: 受け取ったリポジトリで再現結果に到達する
- **対応要求**: 委譲（再現性）, U4, 派生（管理境界インターフェース）
- **典型操作**:
    1. リポジトリを clone
    2. `uv sync` で依存復元
    3. `dvc pull` で実データ復元
    4. `staqkit validate` で整合確認
    5. 必要なら `staqkit repro` で再生成可能性を確認
- **実現区分**: Git+DVC + CLI
- **補足**: 受け渡し側のスナップショット品質次第で操作量が変わる。validate を細分化できれば「最小限の確認」のみで使い始める導線が作れる（→ [idea.md](idea.md)）

### A5. プロジェクトを公開する

- **目的**: 第三者が論文等の根拠データに到達でき、再現できる状態にする
- **対応要求**: U2, U4, 委譲（再現性）, 派生（リポジトリ境界を越えた合成）
- **典型操作**:
    1. 公開対象スナップショットの確定（→ F1）
    2. 意味到達性の最終チェック（→ D7）
    3. リモート（DVC remote, Git ホスティング）への push
- **実現区分**: CLI + Git+DVC + Pattern
- **補足**: 「アーカイブ＝以後編集不可状態」は持たない。公開後のリポジトリも編集可能であり、ある時点のスナップショットが tag として参照可能な状態が「公開」の定義。第三者向け IF は標準構造（stages/, config/, data/stages/）そのものが提供（→ external-data.md「上流の公開IF」）

### A6. 親プロジェクトのデータを参照する形で新プロジェクトを立ち上げる

- **目的**: 1つ以上の既存 staqkit プロジェクトのデータを参照して、新しい解析プロジェクトを開始する
- **対応要求**: 派生（リポジトリ境界を越えた合成）
- **典型操作**:
    1. 新リポジトリを作成（→ A1）
    2. 親プロジェクトのデータを `staqkit import` で取り込む（→ C2）
    3. 新規解析を追加（→ B1）
- **実現区分**: CLI + Pattern
- **補足**: 親が複数（2つ以上の親プロジェクトを持つ立ち上げ）も本シナリオに含む。`dvc import` の標準パターンで親毎に取り込むだけで成立する。テンプレートコピー（親の構造を初期値としてコピーする形）は派生ではなく A4（引き継ぎ受け取り側）と等価のため本シナリオには含めない。**(TODO)** 取り込んだ親データを staqkit Library から読むためのスキーマ取得方針（→ C2 補足、[idea.md](idea.md)「外部 import 時のスキーマ・FK 伝達」）

### A7. 実行環境・依存の更新に追従する

- **目的**: 依存ライブラリ更新（uv lock 更新、Python バージョン更新等）を取り込む
- **対応要求**: 委譲（再現性）
- **典型操作**:
    1. `uv lock --upgrade` で依存更新
    2. `staqkit repro` で全ステージを再実行し結果が一致することを確認
    3. 不一致発生時は原因調査・該当ステージのパラメータ調整
    4. 更新後の `uv.lock` を Git commit
- **実現区分**: CLI + Pattern
- **補足**: 依存環境含めての再現性（委譲する関心）が前提であり、`uv.lock` は Git 管理対象。スナップショット tag は `uv.lock` も含む形で固定される。本シナリオは依存更新に伴う運用ガイドライン的位置付け

### A8. リモートを別に移す

- **目的**: DVC リモート（S3, GDrive 等）または Git ホスティングを別の場所に移行する
- **対応要求**: 委譲（再現性）
- **典型操作**:
    1. 新リモートを設定（`dvc remote add` / `git remote add`）
    2. 新リモートに push（`dvc push` / `git push`）
    3. 旧リモートの参照を切替（`dvc remote default` / `git remote set-url`）
- **実現区分**: Git+DVC
- **補足**: staqkit ラップは不要。DVC/Git の標準操作で完結

### 考慮外シナリオ

以下は本フレームワークのスコープ外として明示する。

- **既存プロジェクトの分割**: 1つの staqkit プロジェクトを複数に分割するシナリオは扱わない。分割が必要な場合は新規プロジェクトを作成し、A6 として既存プロジェクトを親に取り込む形を想定
- **内部構造を維持したままのプロジェクト統合**: 2つの staqkit プロジェクトの内部構造（DAG・stage.yaml 群）を一つにマージするシナリオは扱わない。「2つ以上のプロジェクトを親に持つ新プロジェクト」の形態は A6 で扱う
- **DAG 合成**: 複数の staqkit プロジェクトの DAG 構造を直接共有する形態（submodule 等による DAG 共有）は扱わない。データ参照は A6 / C2 の外部データ取り込みで実現する
- **ブランチ分岐の自動マージ**: 同一プロジェクト内で並走した解析（→ F2 分岐）の自動マージはツール側では保証しない。マージ判断はユーザの責務

## B. 開発・解析作業

日常的な解析作業のシナリオ。

### B1. 新ステージを追加する

- **目的**: 新しい処理ステップを DAG に追加する
- **対応要求**: 派生（拡張性）
- **典型操作**:
    1. `staqkit add-stage <path>` で雛形生成（→ #7）
    2. stage.yaml に inputs/outs/params を記述
    3. run.py に処理を実装
    4. `staqkit validate` で参照整合性確認
    5. `staqkit repro <stage>` で実行
- **実現区分**: CLI
- **補足**: add-stage コマンドは **(TODO)**（→ #7）。実装なしで仕様だけ先に固定する仮追加（planned 状態）は G3 を参照

### B2. パラメータを変えて再実行する

- **目的**: 既存ステージのパラメータを調整して結果を比較する
- **対応要求**: 委譲（部分再生成）, T1
- **典型操作**:
    1. stage.yaml の params を編集
    2. `staqkit repro <stage>` で部分再生成
    3. `staqkit history <stage>` で過去実行と比較
- **実現区分**: CLI
- **補足**: 手動でのパラメータ探索（複数の値を順に試して結果を見る）は本シナリオの繰り返し + E2 履歴一覧 + run_meta のパラメータ記録で対応可能。専用の探索支援機構は持たない。最適化のような自動探索が必要な場合は最適値を出力するステージとして通常通り設計する

### B3. 上流データの更新を下流に伝播させる

- **目的**: 生データや上流ステージの変更を下流ステージに反映する
- **対応要求**: 委譲（DAG整合性・鮮度・部分再生成）
- **典型操作**:
    1. 上流データ変更（生データ差し替え、上流ステージ再実行等）
    2. `staqkit status` で影響範囲を確認
    3. `staqkit repro` で全下流を再生成、または `staqkit repro <stage>` で限定的に
- **実現区分**: CLI
- **補足**: データの後追い追加（少人数被験者で解析実装を済ませてから全被験者データに拡張する等）も「上流データ変更 → 下流再実行」の同型シナリオとして本ケースで扱う

### B4. 特定ステージの上流依存を確認する

- **目的**: 「このステージは何に依存しているか」を把握する
- **対応要求**: U3, T1
- **典型操作**:
    1. `staqkit dag` で全体構造を可視化
    2. 個別ステージの依存は stage.yaml の inputs/extra_deps を参照
- **実現区分**: CLI

### B5. テーブル定義（カラム一覧）を調べる

- **目的**: 「このテーブルにはどんなカラムがあるか」を把握する
- **対応要求**: U3, U4
- **典型操作**: テーブル定義一覧を出力するコマンドを実行
- **実現区分**: CLI
- **補足**: **(検討中)** コマンド名（旧 `staqkit catalog` の責務分割で「定義側」を別コマンドに切り出す方向、→ #10）

### B6. 特定カラムの定義・FK 関係を調べる

- **目的**: 「`uid` ってなんだ？」「どのテーブルにある？」を把握する
- **対応要求**: U3, U4
- **典型操作**: `staqkit column <name>` で全テーブルでの出現箇所と FK 関係を表示
- **実現区分**: CLI

### B7. テーブルの内容（実データ）を一覧する

- **目的**: 「このテーブルに今どんなレコードが入っているか」を把握する
- **対応要求**: U3
- **典型操作**: テーブル内容を出力するコマンドを実行（旧 `staqkit catalog` の責務）
- **実現区分**: CLI
- **補足**: **(検討中)** コマンド名（旧 `catalog` は dkey 必須前提時代の名残、命名再考が必要、→ #10）

### B8. 失敗ステージの原因を調査する

- **目的**: 実行エラーや想定外の出力の原因を特定する
- **対応要求**: T1
- **典型操作**:
    1. `staqkit history <stage>` で過去実行を確認
    2. `staqkit provenance <stage>` で来歴チェーンを辿る
    3. run_meta.yaml で当時のパラメータスナップショットを参照
- **実現区分**: CLI

### B9. ステージを一時休止/再開する

- **目的**: 実験的なステージや一時的に不要なステージを管理から外す/戻す
- **対応要求**: 派生（設計時のステージ状態）
- **典型操作**:
    1. stage.yaml の status を `inactive` に変更
    2. `staqkit clean` で休止データの整理
    3. 再開時は status を `active` に戻して `staqkit repro`
- **実現区分**: CLI + Pattern

### B10. 多軸スライスでデータを取り出す

- **目的**: 「被験者1・条件A・正規化済み」など意味的座標で実データを引く
- **対応要求**: U1, U2
- **典型操作**: notebook/run.py 内で `DataStore.query(table, filters)` を呼ぶ
- **実現区分**: Library
- **補足**: 日常アクセスの中核。CLI ラッパー（探索目的の薄いラッパー）を提供するかは **(検討中)**

### B11. 識別軸メタデータでフィルタする

- **目的**: 「身長 > 170 の被験者だけ」「単位が rad の計測種別だけ」など、識別子の属性に基づくスライス
- **対応要求**: U2（識別子の属性もスライスやフィルタの対象となる、と明記）
- **典型操作**: `DataStore.query()` のフィルタ条件に識別子属性を含める
- **実現区分**: Library
- **補足**: **(TODO)** 識別子属性のフィルタ API 仕様（datastore.md で要確認）

### B12. 新しい被験者・条件を追加する（識別軸の語彙拡張）

- **目的**: 既存の識別軸に新しい値（新被験者ID、新条件名等）を追加する
- **対応要求**: 派生（拡張性）（新しい識別軸の追加、と明記）
- **典型操作**:
    1. table_schemas の該当テーブル定義を更新（新値を許容するスキーマに）
    2. 新データを生成するステージを実行
    3. `staqkit validate` で整合確認
- **実現区分**: CLI + Pattern
- **補足**: **(TODO)** 識別軸の語彙拡張ワークフローの具体仕様

### B13. 識別子の属性を追加・変更する

- **目的**: 被験者IDに体重を後付けする、データ種別の単位定義を変更する等
- **対応要求**: 派生（拡張性）（既存識別子への属性追加、と明記）
- **典型操作**:
    1. table_schemas の該当テーブル定義に column を追加 / 変更
    2. 既存データの再生成または属性付与
    3. `staqkit validate` で整合確認
- **実現区分**: CLI + Pattern
- **補足**: **(TODO)** 属性追加時の既存データ扱い（マイグレーション要否、デフォルト値の扱い）が未仕様

### B14. ステージをリファクタする

- **目的**: 結果（出力データ）を変えずにステージの実装を変更する
- **対応要求**: -（B14 固有の staqkit 責務はなし）
- **典型操作**:
    1. リファクタ前の commit に tag を打つ等で参照可能にする
    2. run.py を編集
    3. `staqkit repro <stage>` で再実行し、リファクタ前と数値が一致することを確認（数値の差分比較はユーザの責務）
- **実現区分**: Library + Pattern
- **補足**: 結果の数値一致を保証する機構は B14 固有では持たない（差分比較はユーザ責務）。一方、出力の「形」については以下が標準提供されており、リファクタ後の repro でも自動的に検査される:
    - 出力スキーマ（カラム構成 vs DDL）の検証 — `DataStore.write_table` 書き込み時（Library）
    - 宣言 outs と実出力ファイルの整合検証 — run_stage エピローグ（Framework）

  したがって「リファクタによりスキーマ契約が壊れた」ケースは repro 時点で検出される。数値比較は F1/F3 のスナップショット参照 + B3 再実行の組み合わせで運用

### B15. ステージを削除する

- **目的**: 不要になったステージを DAG から完全に取り除く
- **対応要求**: 派生（設計時のステージ状態）
- **典型操作**:
    1. 当該ステージを参照する下流ステージの stage.yaml を編集（参照切断 or 代替ソース指定）
    2. 当該ステージのディレクトリ（stages/xxx/, data/stages/xxx/）を削除
    3. `staqkit clean` で残った孤児データを整理（→ D11）
    4. `staqkit validate` で参照整合性を確認
- **実現区分**: CLI + Pattern
- **補足**: **(TODO)** 下流が当該ステージを参照したまま削除しようとした場合の扱い（validate でブロックするか警告のみか）。B9 一時休止との違いは「永久削除」である点

### B16. 識別子の値を削除する

- **目的**: 既存の識別軸から特定の値（被験者 ID、条件名等）を取り除く
- **対応要求**: 派生（拡張性）（B12 の逆操作）
- **典型操作**:
    1. table_schemas の該当テーブル定義を更新（該当値を許容しないスキーマに）
    2. 当該値を参照する既存データを削除または再生成
    3. `staqkit validate` で参照整合性を確認
- **実現区分**: CLI + Pattern
- **補足**: **(TODO)** 当該値を参照する既存データの扱い（強制削除 / 孤立検出 / 警告のみ）が未仕様。B15 ステージ削除と同じく参照整合性検査の方針整備が必要

## C. 外部成果物・連携

成果物の外部利用と外部リポジトリとの連携。論文・レポート等の特定用途は本カテゴリの一般シナリオで扱い、専用シナリオは設けない。

### C1. 成果物を外部にエクスポートする

- **目的**: ステージ出力データを外部用途（論文、レポート、別解析プロジェクト等）で利用可能にし、来歴も含めて第三者に追跡可能な形で提供する
- **対応要求**: U2, 委譲（再現性）, T1
- **典型操作**:
    1. 出力したいデータを生成するステージを `staqkit repro` で確定
    2. 出力対象は `data/stages/<stage>/` の parquet として既に確定済み
    3. 配布手段はユースケースに応じて選択:
        - 同プロジェクトの clone を共有（最も再現性が高い）
        - 別 repo から `dvc import` で参照（→ C2）
        - parquet を手動コピー（来歴は別途明示）
    4. 来歴は `staqkit provenance <stage>` で取得し、run_id・commit hash を成果物に併記
- **実現区分**: CLI + Pattern + Git+DVC
- **補足**: 専用 export コマンドは持たない。出力データは必ずステージ出力として運用することで来歴を保証する設計が前提（中間生成物を export 対象にする場合は、別ステージとして DAG に組み込む）。論文・レポート等の特定用途も本シナリオで扱い、用途別の特別な処理は設けない

### C2. 別リポジトリのデータを取り込む

- **目的**: 他プロジェクトの解析結果を入力ノードとして利用する
- **対応要求**: 派生（リポジトリ境界を越えた合成）
- **典型操作**: `staqkit import --repo <url> --stages <list>` で取り込み（→ external-data.md）
- **実現区分**: CLI
- **補足**: **(TODO)** 取り込んだ parquet を staqkit Library から読むには対応する `config/table_schemas/` が必要だが、`dvc import` で伝達されるのはデータ実体のみで table_schemas は伝達されない。スキーマ取得方針は未確定（→ [idea.md](idea.md)「外部 import 時のスキーマ・FK 伝達」）。A6 親プロジェクト参照立ち上げでも同じ問題が出る

#### C2a. 取り込みノードの来歴を出典元 DAG まで追跡する

- **目的**: 取り込んだデータが出典元でどう生成されたかを辿れる
- **対応要求**: T1（出典元 DAG への参照を通じて来歴が追跡可能、と明記）
- **典型操作**:
    1. 取り込みデータの `.dvc` ファイルから `repo.url` と `rev_lock`（commit hash）を取得
    2. 出典元リポジトリを別途 clone（`git clone --branch <hash>` 等）
    3. clone 先で通常の `staqkit provenance` を実行
- **実現区分**: Git+DVC + Pattern
- **補足**: `dvc import` が記録する `rev_lock` + `repo.url` がスナップショット参照として機能する。staqkit 側の追加ラップは不要。フレームワーク責務は「参照を辿れる構造を保証する」ことに留まり、辿る操作自体はユーザが Git で行う（→ external-data.md「上流DAG理解」）。`staqkit import` 時に出典元の run_meta.yaml を自リポへ同梱する仕様は持たない（必要な場合は出典元 clone で取得可能、また run_meta は git のみで参照可能なため DVC remote へのアクセス不要 → stage.md「データ実体との独立性」）

#### C2b. 取り込み元 DAG の更新を反映する

- **目的**: 出典元リポジトリの最新版を自プロジェクトに取り込み直す
- **対応要求**: 派生（リポジトリ境界を越えた合成）
- **典型操作**: `dvc update data/external/<source>/<stage>/` で一括更新
- **実現区分**: Git+DVC
- **補足**: external-data.md「取り込み」で `dvc update` による明示的追従が方針として確定。更新検知の自動化は現状未対応（手動判断）

#### C2c. 自プロジェクトの一部を外部公開 IF として整備する

- **目的**: 他プロジェクトから取り込まれることを前提に、自プロジェクトの出力を整備する
- **対応要求**: 派生（リポジトリ境界を越えた合成）（U2, U3, U4 が外部に対しても成立することの確認）
- **典型操作**: 通常の運用（standard structure 維持 + description 充実 + スナップショット確定）でそのまま外部公開 IF として機能
- **実現区分**: Pattern
- **補足**: 標準構造（stages/, config/, data/stages/）自体が外部 IF として機能するため、追加整備は原則不要（external-data.md「上流の公開IF」）。整備対象は通常の品質改善（→ D7 description 網羅、A5 公開シナリオ）と同じ

### C3. プロジェクト構造ドキュメントを書き出す

- **目的**: README や docs 用に DAG 構造・テーブル定義一覧をドキュメント化する
- **対応要求**: U4, 派生（リポジトリ境界を越えた合成）
- **典型操作**:
    1. 必要な情報を出力する B 系コマンドを実行（B5 テーブル定義一覧、B6 column、B7 テーブル内容、D12 dag 等）
    2. stdout をパイプで Markdown ファイル等に保存
    3. リポジトリ内 docs に配置
- **実現区分**: CLI + Pattern
- **補足**: staqkit が提供するのは stdout 出力までであり、ファイル書き出しやフォーマット変換のパイプ処理は責務外。基本的には B 系コマンドの組み合わせで対応する。**(検討中)** ドキュメント書き出し用途でのみ求められるコマンド（サマリ化等）がないか（C 単独で求められる固有コマンドの有無）

## D. 健全性・検証

リポジトリの整合性・鮮度・再現性確認。validate 内部の各検査項目を独立 UC として並列に立て、validate 細分化検討（→ [idea.md](idea.md)「編集時バリデーション支援」）の根拠とする。

### D1. stage.yaml の構文・外形を検証する

- **目的**: stage.yaml の必須フィールド・型・構造が正しいことを検査する（個別ファイル単体の外形検査）
- **対応要求**: 検証（自己契約の再帰）
- **典型操作**: `staqkit validate` を実行（現状はフルチェックの一部として実行）
- **実現区分**: CLI
- **補足**: 実装は Pydantic（StageDefinition）。本 UC はステージ間参照や DAG 構造を見ない単体検査であり、参照整合性は D4 で扱う

### D2. table_schemas 定義の構文・外形を検証する

- **目的**: `config/table_schemas/*.yaml` の必須フィールド・型・構造、および埋め込み DDL の構文を検査する
- **対応要求**: 検証（自己契約の再帰）
- **典型操作**: `staqkit validate` を実行（現状はフルチェックの一部として実行）
- **実現区分**: CLI
- **補足**: 実装は Pydantic（TableSchemaSet）+ sqlglot（DDL 構文パース）。本 UC は単体ファイルの外形検査であり、テーブル間の FK 整合性は D6 で扱う

### D3. その他 staqkit 独自定義ファイルの構文・外形を検証する

- **目的**: stage.yaml / table_schemas 以外で staqkit が要求する独自フォーマットファイル（run_meta.yaml, column_descriptions yaml 等）の構文・外形を検査する
- **対応要求**: 検証（自己契約の再帰）
- **典型操作**: `staqkit validate` を実行（現状はフルチェックの一部として実行）
- **実現区分**: CLI
- **補足**: **(TODO)** 検査対象ファイルの具体的列挙は実装時に確定。D1/D2 を主要検査として独立させ、本 UC はキャッチオールとして残りをまとめる

### D4. 参照整合性をチェックする（DAG 構造）

- **目的**: stage.yaml 間の `source_stage` 参照が実在し、循環していないことを検査する
- **対応要求**: 検証（自己契約の再帰）
- **典型操作**: `staqkit validate` を実行（現状はフルチェックの一部として実行）
- **実現区分**: CLI
- **補足**: validate 細分化により本検査だけ単独実行する仕組みは **(TODO)**（→ [idea.md](idea.md)「編集時バリデーション支援」）

### D5. データのスキーマ準拠をチェックする

- **目的**: `data/stages/*` の parquet ファイルが `config/table_schemas/` の DDL に準拠していることを検査する
- **対応要求**: M1 契約強制
- **典型操作**: `staqkit validate` を実行（現状はフルチェックの一部として実行）
- **実現区分**: CLI
- **補足**: ステージ実行時の書き込みでは `DataStore.write_table`（Library）が同等検査を行う（→ B14）。本 UC は「リポジトリ全体の parquet を横断検査する」役割

### D6. テーブル間の FK 整合性をチェックする

- **目的**: TableSchemaSet の FK 参照先テーブルが存在し、型が一致することを検査する
- **対応要求**: M1 契約強制
- **典型操作**: `staqkit validate` を実行（現状はフルチェックの一部として実行）
- **実現区分**: CLI

### D7. description 網羅をチェックする

- **目的**: ノード・カラムに対する説明（stage.yaml の desc 欄、各 stage の README.md、column_descriptions）の欠落を検出する
- **対応要求**: U4
- **典型操作**: `staqkit validate` の警告項目として検出
- **実現区分**: CLI
- **補足**: 部分対応（column_descriptions 未記述警告は実装方針が確定）。本 UC は外形 valid（D1〜D3）を前提に「説明欄が埋まっているか」「説明系ファイルが配置されているか」を見る位置づけ。**(TODO)** 3 層構造（説明欄充足 + 説明系ファイル存在）の網羅検査仕様

### D8. パラメータと実データの整合性を点検する

- **目的**: stage.yaml の params と実データ（run_meta のスナップショット）が乖離していないことを確認する
- **対応要求**: T1
- **典型操作**: `staqkit validate` または `staqkit status` の検査項目に含める
- **実現区分**: CLI
- **補足**: **(TODO)** validate の検査項目に明示的に追加するか、status の責務にするかの整理

### D9. 各ステージの鮮度を確認する

- **目的**: どのステージが再実行を要するかを把握する（上流データ変更による下流の鮮度低下検出）
- **対応要求**: 委譲（DAG整合性・鮮度）
- **典型操作**: `staqkit status` を実行
- **実現区分**: CLI
- **補足**: dvc.yaml は staqkit 全体として派生物扱いであり Git 非管理（→ [architecture.md](architecture.md) / [components/pipeline-gen.md](components/pipeline-gen.md)）。`staqkit status` は repro 等と同じ生成プロローグを共有した上で `dvc status` を呼ぶラッパーであり、動的生成は本 UC 固有の付加価値ではない。`dvc status` の出力分類のうち changed deps が本 UC の主関心、missing data + changed outs は再現性確認（→ D10）の関心。**(検討中)** planned/inactive の表示や stage 状態併記など、出力フォーマット拡張の要否

### D10. スナップショット再現性を確認する

- **目的**: clone した状態が固定スナップショットと一致しており、再現可能な状態にあることを確認する
- **対応要求**: 委譲（再現性）
- **典型操作**:
    1. リポジトリを clone
    2. `uv sync` で依存復元
    3. `dvc pull` で実データ復元
    4. `staqkit status` で差分なし（全ステージが up-to-date）を確認
- **実現区分**: CLI + Git+DVC
- **補足**: A4 受け取り側の最終チェックとしても利用される。**(検討中)** 「再現できているか」を明示判定する専用フラグ（`staqkit status --check` 等）を提供するか、`staqkit status` の出力解釈で十分か

### D11. 孤児・inactive データを整理する

- **目的**: 不要なデータディレクトリを検出・削除する
- **対応要求**: 派生（設計時のステージ状態）
- **典型操作**: `staqkit clean` で検出 → `--remove` で削除
- **実現区分**: CLI

### D12. パイプライン全体像を見る（planned 含む）

- **目的**: 未生成ステージも含めた全体構造を視覚化する
- **対応要求**: U3, 派生（設計時のステージ状態）
- **典型操作**: `staqkit dag` を実行
- **実現区分**: CLI

### D13. 出典元 DAG との参照リンク切れを検出する

- **目的**: 取り込み済みノードの出典元参照が解決可能かを検査する
- **対応要求**: 派生（リポジトリ境界を越えた合成）, T1
- **典型操作**: `staqkit validate` の検査項目として検出
- **実現区分**: CLI
- **補足**: **(TODO)** クロスリポ整合性検査の仕様

## G. 管理境界

管理下と管理外（notebook 等）の境界をまたぐ操作。

### G1. notebook 探索結果を管理下に昇格させる

- **目的**: notebook で得た探索結果を staqkit ステージとして固定する
- **対応要求**: 派生（管理境界インターフェース）, 文脈（探索的ワークフロー）
- **典型操作**:
    1. notebook で得たコード・データを stage.yaml + run.py に翻訳
    2. 出力 IF（outs）を宣言
    3. `staqkit repro <stage>` で管理下に確定
- **実現区分**: Library + CLI + Pattern
- **補足**: 翻訳作業自体はユーザの責務。staqkit が提供するのは昇格先の構造（stage.yaml/run.py 規約）と、昇格後に notebook 側から管理下データを参照可能にする Library（→ G2）。専用支援コマンドは持たない

### G2. 管理下データを管理外環境から消費する

- **目的**: notebook やアドホックスクリプトから staqkit 管理下のデータを読む
- **対応要求**: 派生（管理境界インターフェース）
- **典型操作**: notebook 内で `from staqkit import DataStore` → `query()` で取得
- **実現区分**: Library

### G3. 出力 IF を先に定義して planned ノードを作る

- **目的**: 実データ未生成のまま下流の処理ステップを設計する
- **対応要求**: 派生（設計時のステージ状態）, 基盤モデル（ノード状態）
- **典型操作**:
    1. stage.yaml に `status: planned` で outs 宣言
    2. 下流ステージは planned ノードを参照可能
    3. 後で run.py を実装 → `status: active` → `staqkit repro`
- **実現区分**: CLI + Pattern
- **補足**: `staqkit add-stage --status planned` で支援可能（→ #7）
